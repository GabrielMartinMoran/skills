# Language and visual patterns

Apply these patterns after the information architecture is sound. Preserve
meaning, formal terminology, and necessary qualifications.

## Sentences

- Put the actor, action, and object close together.
- Prefer active voice when the actor matters or the passive hides responsibility.
- Use a concrete verb instead of a noun-heavy phrase.
- Remove filler such as "in order to," "at this point in time," and "is able to"
  when a shorter accurate alternative exists.
- Replace ambiguous pronouns with the noun when two antecedents are possible.
- Split a sentence when it contains separate decisions, conditions, or actions.
- Keep necessary technical vocabulary and define it; do not replace precision
  with a familiar but inaccurate word.

## Paragraphs

Give each paragraph one dominant topic. Use the opening sentence to state the
point, then add evidence, explanation, conditions, or an example. Break a
paragraph when its purpose, audience assumption, or action changes.

Short paragraphs are a scan aid, not a target to satisfy mechanically. A longer
paragraph is acceptable when its sentences form one coherent argument and the
opening and transitions keep the relationship visible.

## Lists

Use a list when the reader benefits from seeing items as a group.

- Use bullets for unordered or parallel items.
- Use numbers for sequence, priority, or a countable set of steps.
- Start items with a consistent grammatical form.
- Keep items concise enough to scan. Give long items a bold lead or a heading,
  or convert them into subsections.
- Split long lists by concept and name each group.
- Introduce the list with a complete sentence rather than an unfinished fragment.

## Tables

Use a table for repeated fields or genuine comparisons. Give columns clear names,
keep cells parallel, and avoid putting long explanations in cells. Convert a
table to headings or lists when readers need to read one item from top to bottom,
when the content is sequential, or when the table will be hard to read on small
screens or with assistive technology.

## Code and technical notation

Use code formatting for commands, filenames, symbols, identifiers, and literal
values. Label examples by purpose. Show expected output when it confirms
success. Keep prose instructions outside the code block so the reader can tell
what to copy, what to edit, and what to expect.

Never alter a command, parameter, number, or formal expression for style. If a
technical example is simplified, label what it omits.

## Emphasis and callouts

Use one visual signal for one reason:

- **Bold:** a short key term or scan target.
- *Italics:* limited secondary emphasis or a defined term where the style guide
  supports it.
- Callout: a warning, constraint, definition, decision, or unusually useful
  example.
- Code block: exact material.

Keep emphasis sparse. If most of a section is bold, nothing is prioritized. Do
not use color, emoji, capitalization, or decoration as the only way to convey
meaning. Every callout should earn its visual weight.

## Links and media

Write link labels that make sense out of context. Describe the destination or
action. Provide alt text that communicates the purpose of an informative visual;
use empty alt text for purely decorative images when the medium supports it.
Do not add an image merely to break up text if it adds no information.

## Medium adaptation

- **Markdown:** use semantic headings, lists, code fences, descriptive links,
  and whitespace. Do not rely on color or layout that a renderer may remove.
- **HTML or rich documents:** preserve semantic structure, focus order, contrast,
  scalable text, keyboard access, and user control over moving or changing content.
- **Plain text:** use labels, indentation, blank lines, short sections, and
  explicit transitions. Make the hierarchy understandable without styling.
