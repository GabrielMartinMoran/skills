# Document modes

Choose a primary reader need before choosing headings. A document can contain
multiple modes, but each section should make its purpose clear.

## Tutorial

Use when the reader is learning through a guided experience.

Recommended shape:

1. State the outcome and what the reader will build or understand.
2. List prerequisites and what the reader can expect.
3. Guide one meaningful path with visible checkpoints.
4. Explain only the concepts needed at each point.
5. End with a working result and next learning paths.

Keep the path safe and coherent. Link to reference material instead of
interrupting the learning flow with every possible option.

## How-to guide

Use when the reader has a goal and needs to complete it.

Recommended shape:

1. Name the goal in the title.
2. Show the result, prerequisites, and important constraints first.
3. Give one action per step when actions have separate decisions or outcomes.
4. Put conditions before the action they constrain.
5. Show expected output and recovery steps for likely failures.

Do not turn a how-to into a general explanation. Link to background when it is
useful but not required for the task.

## Reference

Use when the reader needs accurate lookup information.

Recommended shape:

1. State what the subject is and where it applies.
2. Use stable, predictable headings for each concept or field.
3. Put syntax, parameters, types, defaults, constraints, and examples near the
   item they describe.
4. Make edge cases and version differences easy to find.
5. Keep explanation separate from the authoritative definition.

Completeness matters more than conversational flow. Use summaries and navigation
to make completeness navigable instead of deleting valid detail.

## Explanation

Use when the reader needs a mental model, rationale, history, or tradeoff.

Recommended shape:

1. State the question or problem.
2. Give the short answer or central model.
3. Build the reasoning in an order the reader can follow.
4. Compare alternatives and name tradeoffs.
5. Close with implications and links to action or reference.

Do not hide the answer behind a long introduction. Use signposts when the
reasoning must precede the conclusion.

## README

Optimize for orientation and a fast first success.

Recommended shape:

1. Project name and one-sentence purpose.
2. The problem solved, audience, and current status.
3. Quick start with the smallest successful path.
4. Installation or prerequisites.
5. Common usage and concrete examples.
6. Links to architecture, reference, guides, configuration, and contribution
   material.
7. Support, limitations, security notes, and next steps where relevant.

Keep the README as a map. Move exhaustive reference material to linked pages.

## Decision or policy document

Optimize for a decision, its consequences, and its boundaries.

Recommended shape:

1. Decision or policy statement.
2. Scope and who is affected.
3. Why this exists and which problem it addresses.
4. Required behavior, constraints, and exceptions.
5. Alternatives considered and tradeoffs.
6. Rollout, ownership, review date, or next action.

Keep rationale and requirements visibly distinct. A reader should not have to
infer which sentences are mandatory.
